# 依賴層與專案碼層要分屬不同容器層

**可判斷主張**：拿一個多階段 Docker build 問「改一行專案程式碼，node 需不需要重拉那 ~1GB 的依賴層？」
——不需要（依賴層輸入只有 `pyproject.toml`+`uv.lock`），屬這個概念；把「大依賴 + 小專案碼」放同一 COPY
層、改碼就換整層 digest，就是反例（慢拉治本前的狀態）。

## 一句話

Python 容器通則：依賴 from lock 裝進 site-packages（一層）、專案碼從 `src/` 跑（另一層）；碼改動不動依賴層，
node 命中既有快取、不再慢拉。

## 為什麼是它（剪枝力）

- **慢拉事故的根**：Dockerfile 用 `uv pip install .`（讀 pyproject range、把 `ai_api` 也烤進 site-packages），
  runtime 把整個 site-packages 當**單一 COPY 層** → 改一行碼就換掉整層 digest → 每次部署重拉整包（~1GB、學校
  上行慢 20+ 分）→ helm hook 等不到 image → hook timeout → 整個 upgrade 回滾。
- **治本**：`uv export --frozen --no-dev --no-emit-project` → `uv pip install --system -r`（依賴 pinned from
  uv.lock、排除專案本身）；專案碼改成 runtime `COPY src/ ./src/` + `PYTHONPATH`。兩效果：① 可重現 ② 快取穩定。
- **前置驗證**：`import ai_api`、ASGI 建構、`python3 -m alembic/uvicorn/ai_api.cli.create_admin` 全走 `python3 -m`、
  無 `importlib.metadata` 自我版本依賴，故專案不需被 pip 安裝。
- **診斷法**：helm hook 逾時最常見主因是「node 拉新 image 太慢」不是 hook 邏輯錯；先看 pod 是否卡在
  `ContainerCreating/Pulling`；**慢拉 vs 壞拉**——只有 `Pulling`、無 `Failed/Back-off` = 慢。治標＝ warmer Pod 預拉。
