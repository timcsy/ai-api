# 同一件事只能有一條可改寫的路徑（其餘 derive 或只當 bootstrap fallback）

**可判斷主張**：拿一個治理決策（誰能存取、配額多少、哪些 redirect 可放行）問「系統裡有幾條路徑能改寫它？」
——恰好一條、其餘 derive 自它或只在它不存在時生效，屬這個概念；有兩條並行可改，就是反例（必 drift）。

## 一句話

多條路徑管同一件事 → 管理員必然忘了同步其中一條 → 使用者被無聲擋下；設計時就要回答「誰是這件事的
source of truth」。

## 為什麼是它（剪枝力）

- **白名單事故**：白名單與成員清單兩條路徑管 access → admin 在 `/admin/members` 加的人被白名單擋、老師收到「this
  account is not allowed」。解法：白名單退為 **bootstrap-only**（DB 無 admin 才查），成員清單為單一真理。
- **顯示 ≠ 執法**：用同一 Helm value 同時注 nginx + backend env，避免「UI 寫 100MB 但 nginx 還是 1MB」。
- **一個語意旗標多用途**：`is_service_allocation` 同時豁免 rebalance 與 anomaly，不為每個機制各加專用 exempt 旗標。
- **UI 表面也要成立**：原則 1 的「撤銷單一憑證不影響其他」若在 UI 看起來只影響單一 model（實則連坐），承諾就
  被架空——把金鑰區降唯讀、列出連坐範圍、撤回確認明示。「承諾要在 UI 表面成立、不只在資料層成立」。

## 「bootstrap-only fallback」是把這原則寫進程式的好模式

平時不在路徑上、不會 drift，緊急時還在（首位 admin、env→DB 單例的 env 預設皆此形）。
