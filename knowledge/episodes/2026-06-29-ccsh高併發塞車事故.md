# 2026-06-29 · ccsh 遷入後高併發塞車事故（誤判彎路 → 治本）

## 為何（why）
ai-api 遷入第二座叢集（ccsh、與 tew 並存）後，研習/人潮下 `/v1/responses` 大量 500。

## 怎麼（how / 診斷與誤判彎路）
- `pg_stat_activity` 50 條 active 卡死、最久 **1004 秒**，全是同一句 `UPDATE provider_credentials … last_used_at`；
  而 CPU 全程 **12% 很閒**——症狀像「算力/連線不夠」，根因是「鎖持有時間 × 共用單把 Azure key 熱列 × 併發」。
- **誤判彎路**：先當容量問題加 pod（2→5）+ 加大連線池——治標、甚至更糟（更多連線搶同一列）。
- **治本**：`get_next()` 的 `last_used_at` flush 從請求 session 改**獨立短交易立即 commit**（鎖只持毫秒、絕不
  跨外部慢呼叫）+ 可調池 + `pool_pre_ping`。修後連線 79→5、active 51→1、卡死 UPDATE 50→0、500 歸零。

## 用了哪些概念
「熱列鎖不可跨外部慢呼叫」；既有 app-key `last_used_at` 早有 >5min 節流、provider-cred 這條漏了——同類
bookkeeping 要套同一防護。
